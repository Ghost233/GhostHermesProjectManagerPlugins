# Hermes 开发协作插件简化首版规格

状态：Q1 至 Q10 与公共测试接缝已确认，规格已发布到跟踪器并添加 ready-for-agent。本文不表示新方案已经实现或验收通过。

## 问题陈述

用户希望从飞书向总管提出开发需求，由各仓库负责人监督本机 DSH 完成详细规划、开发、测试和审查。工作涉及多个仓库时，各仓库独立细拆，完成后按需要协调验证。用户希望及时看到需求分歧和阻塞问题，并像 grilling 一样直接回答。

原方案把公开机器人交接、自建管理界面、独立调度、完整聊天关联、资料迁移和档案管理纳入同一首版，增加了运行依赖与验收范围。用户当前没有残留运行任务，系统尚在开发，允许按新范围替换未完成的设计和实现。

本规格先完成从开发请求到真实交付的流程，复用原生任务派发与 DSH 工作流。旧工单与旧测试保留为原方案参考，不要求原样补齐，也不自动作为本规格的通过证据。

## 解决方案

总管接收需求，确认目标项目与仓库，内部派发完整工作。原生 Kanban 是唯一的外层派发入口，仓库负责人监督自己的专用 DSH 实例。DSH 在仓库内按 Matt 详细拆分、实施、测试和审查，Hermes 汇报关键事件并处理人工问题。

每个仓库的完整工作对应一个总 Issue 和一张外层任务卡。细任务 Issue 留在 GitHub，避免逐票镜像与重复派发。飞书展示关键交接、需求分歧、接口变更、阻塞和结果，完整聊天保存在受限本机。

普通提问和规划确认通过飞书分次回答，收齐一轮后送回原 DSH 任务。具体执行审批在本机 DSH 原生界面处理。首版只管理专用实例及实测受控的工具和后台任务，未知状态如实报告并限制后续派发。

## 用户故事

1. 作为用户，我希望在飞书向总管提出需求或指定总 Issue，从而通过一个日常入口分配开发工作。
2. 作为总管，我希望把跨仓库需求分成明确的仓库级工作，从而让各负责人独立完成自己的范围。
3. 作为用户，我希望负责人绑定现有本地仓库，从而直接使用我的本机工作区。
4. 作为用户，我希望保留总管、项目总负责人和子项目负责人等责任角色，并允许合并后两层，从而按项目规模安排责任。
5. 作为没有自身仓库的调度负责人，我希望只派发和汇总，从而无需自动生成 mono 仓库或额外测试工程。
6. 作为用户，我希望仍能直接 @ 负责人或独立助手，从而保留已有沟通入口。
7. 作为仓库负责人，我希望完整工作对应一个总 Issue 和一张外层任务卡，从而能跟踪派发、进展和交付。
8. 作为 DSH 执行者，我希望在总 Issue 内按 Matt 详细拆分细任务 Issue，从而使用仓库上下文规划实现。
9. 作为仓库负责人，我希望细票只在 GitHub 管理，从而避免每张细票再次触发 Hermes 派发。
10. 作为用户，我希望原生 Kanban 唯一管理外层队列，从而避免两套队列同时启动同一工作。
11. 作为用户，我希望同一逻辑仓库的外层任务串行、不同仓库可以并行，从而减少工作区冲突。
12. 作为用户，我希望看到关键交接、需求分歧、接口变更、阻塞和结果，从而及时纠正方向。
13. 作为用户，我希望有活动任务时收到定期摘要，从而了解运行状态而无需阅读完整聊天。
14. 作为用户，我希望每轮 grilling 问题带有题号、选项和必要材料，从而能够审阅并回答。
15. 作为用户，我希望引用原提问并真实 @ 发问机器人回复，从而沿用现有收件权限并关联正确任务。
16. 作为用户，我希望一轮问题可以分次回答，从而先处理已经明确的部分。
17. 作为用户，我希望未答问题保持待答，明确跳过或委托决定时保留原答复，从而避免自动把沉默当作同意。
18. 作为用户，我希望普通问题和规划确认回到同一 DSH 任务，从而继续原来的 Matt 流程。
19. 作为用户，我希望超时后仍有效的原问题能够继续回答，从而无需重新发起工作。
20. 作为用户，我希望重复、失效、错投或已经在原界面处理的答复不触发新执行，从而避免重复输入。
21. 作为用户，我希望具体执行审批在可达的 DSH 原生界面审阅，从而区分规划决定与操作许可。
22. 作为用户，我希望敏感值不进入群消息或插件问答记录，从而保护凭据和私人输入。
23. 作为用户，我希望只管理 Hermes 创建的专用 DSH 实例，从而先明确执行归属。
24. 作为用户，我希望只启用实际通过测试的原生工具和后台任务，从而知道首版支持范围。
25. 作为用户，我希望停止任务后保留改动，并核实执行与仓库状态，从而安全安排后续工作。
26. 作为用户，我希望停止范围无法确认时保留未知与仓库占用，从而避免下一项工作与未结束执行冲突。
27. 作为用户，我希望重启、失联或 Kanban worker 重排时先核对原 DSH 工作，从而避免重复启动和盲重送。
28. 作为仓库负责人，我希望按总 Issue 核对实际测试、交付版本、PR 和遗留项，从而提供可验证的交付。
29. 作为用户，我希望 PR 审查、待合并和已合并状态单列，从而不把卡片完成误认为代码已经合并。
30. 作为用户，我希望远端更新后对应本地分支同步，并保护已有修改，从而继续使用我的主工作区。
31. 作为用户，我希望原生记录和非秘密运行日志仅在受限本机保存，从而保留必要诊断而不公开个人绑定。
32. 作为用户，我希望插件使用原生扩展接口并保持 SDK 源码不变，从而能够独立安装、卸载和重新加载。

## 实现决策

### 原生派发与仓库工作

- 原生 Kanban 是唯一的外层派发者。停用其内置自动拆分，由 DSH 主持 Matt 的仓库内细拆。插件停止维护第二套自动派发队列。
- 一个总 Issue 对应一张仓库级外层任务卡。细任务 Issue 由 DSH 工作流在 GitHub 管理，不逐张复制为 Kanban 卡。
- 保留责任角色与开发监督能力的区分。只有明确登记仓库的负责人承担该仓库开发或验证，未指定的 submodule 不自动创建负责人。
- 每次完整工作使用独立 DSH 会话，追加、问题回答和明确继续关联原工作。子代理和内部并行属于该外层任务。
- 仓库互斥基于同一逻辑仓库，不能借不同路径、Profile 或卡片身份绕过。同仓外层任务串行，不同仓可并行。
- 必要跨仓验证由明确指定且有对应仓库的负责人承接，调度负责人汇总；不自动创建新仓库，也不自行修改其他仓库源码。

### 插件接口与最少状态

- 复用 Hermes 的平台、工具、Hook、后台任务和卸载接口，以及原 DSH 的受支持启动与调用接口。
- 插件保存外层卡、总 Issue、逻辑仓库、负责人、专用实例与原会话的最少对应，以及输入意图、问题轮次、答复、占用和验收证据。调度状态沿用原生 Kanban，不复制一套任务板状态机。
- 对外请求不能通过自称身份、角色、目录或权限来提升操作范围。真实平台身份、登记职责与当前工作授权决定可用动作。
- 身份核验、真实 @、职责授权、稳定去重、消息关联、重连与资源清理继续有效。
- 使用现有本地仓库及受限配置中的绑定，不默认 clone，也不以额外工作区替代用户主工作区。模型与预算通过获准的专用原生配置引用接入并实际验证。
- 不修改原生数据库结构或 SDK 源码，不注册配套认证组件，不全局替换宿主 logger 或信号处理。

### 飞书与人工应答

- 内部交接承担工作派发；飞书承担输入、关键事件通知、摘要和人工问答，不逐条镜像机器人或 DSH 聊天。
- 每轮提问用一条消息呈现，保留原题号、选项和必要上下文，并提供可读的待确认材料或受限附件。
- 当前收件入口要求真实 @。提问指明引用原消息并通过平台选择器 @ 发问机器人，不为此扩大到读取整个群的聊天。
- 分次答复按原轮次收集，显示已答和待答项，收齐后整轮回送。明确跳过或委托决定按用户原意记录；未答问题不默认同意。
- 普通文字提问作为原会话的后续输入，结构化提问回应原请求。区分仍有效的 live、超时过渡及 continued 路径，不用普通 prompt 冒充结构化应答或审批。
- 回送前确认原工作、问题和答复仍有效。不能唯一关联时澄清；重复、失效、已经处理或发送结果未知的输入不盲重送。
- 普通问答与规划确认可在飞书处理，具体执行审批在本机 DSH 原生界面处理。界面必须可达并能定位正确任务，批准或拒绝后的实际状态回流。
- 群里不输入敏感值，插件不复制原界面的敏感答复。规划确认不新增目录职责、工具权限或长期授权。

### 执行、停止与恢复

- 首版只管理 Hermes 为项目创建的专用 DSH 实例与任务，不观察或接管 Desktop 手动会话。
- 只开放实际验收受控的原生开发工具和后台任务，逐入口验证仓库写入、越界拒绝和停止结果。cwd、权限模式名称和专用实例本身不作为保护证据。
- 原生日志与任务状态中记录实际运行版本、实例和连接代次。SDK 源码存在某种能力不等于当前组合已通过验证。
- 停止结束当前外层工作并保留改动。只有确认相关执行结束并核对仓库状态，才释放占用安排后续任务；未知范围暂停该仓库后续派发。
- 原生 Kanban worker 的退出或重排不等于 DSH 任务结束。worker 恢复时先核对并附着已有工作，不能仅因重排再次创建会话或发送原输入。
- 重启、失联与未知结果先核对原工作；执行中恢复监督，明确停止的工作不自动继续。无法确认时报告未知，不把超时视作完成。
- 自有连接、订阅、任务和专用进程按真实归属清理；共享或不属于当前工作的执行不因卸载而被中断。

### 交付与资料保护

- 外层任务按总 Issue 验收，核对工作范围、实际测试、固定交付版本、PR 和遗留项。模型一轮结束或卡片状态不单独作为交付证据。
- PR 审查和合并状态分别报告。只有任务明确要求且拥有实际授权时才合并；远端更新后对应本地分支仅作 fast-forward 同步，保护已有修改。
- 有活动工作时每 15 分钟汇总。需要用户处理的阻塞、审批与交付结果及时通知；明确等待不误报卡死，重复事件不重复告警，无活动不刷屏。
- 原生任务和会话记录限于受限本机，原生日志可保存非秘密项目名称、路径等绑定。实际目录、文件、符号链接与日志采集权限须核验。
- 凭据不得进入普通诊断日志、群消息或公开产物。群通知仅包含允许分享的内容，插件源码、测试、版本化文档和公开 Issue／PR 仍使用合成引用。

## 测试决策

### 主要测试接缝

优先复用现有原生插件入口：从受控飞书收件事件进入实际注册的平台、工具与 Hook，驱动原生 Kanban 和 DSH 接入，以用户收到的消息、原任务状态、卡片、Issue 与实际交付结果作断言。

这是一处贯穿主要流程的公共入口，避免为了测试增设独立控制 API。普通问答通过同一入口回送；执行审批由原生 DSH 界面操作，作为真实环境验收的一部分。插件加载、卸载和重载复用原生生命周期入口。

离线测试只替换飞书、GitHub 等外部服务边界，用合成身份与仓库覆盖确定性场景。原生 Kanban、Hermes 注册生命周期及 DSH 协议使用未经修改的实际实现；真实模型、飞书事件和 DSH 操作另行实测，离线替身不代替通过结论。

### 测试质量与可复用证据

- 测试外部行为、实际结果和持久对应，不检查私有函数布局、消息计数偶然值或内部字段排列。
- 复用现有受控飞书服务边界、原生 SDK 加载与生命周期、原 DSH 启动与协议、任务控制、去重和重启核对测试的有效接缝。
- 旧 Dashboard、逐细票队列、Desktop 手动会话和广泛资料管理测试不成为新首版硬门禁；必要覆盖按新行为迁移，旧通过数量不自动继承。
- 测试保存实际输入、源码版本、命令、退出结果和资源清理证据。失败、超时、取消、未知或缺证据不能记为通过，强制清理不能冒充原生正常退出。

### 核心验收场景

| 场景 | 外部行为与通过条件 |
| --- | --- |
| 单仓开发 | 一条获准请求产生唯一外层卡与正确总 Issue，绑定正确本地仓库和专用会话；DSH 创建细票并取得真实开发、测试和审查结果 |
| 多仓与互斥 | 不同仓工作可并行，同一逻辑仓库第二项工作等待；路径或 Profile 别名不能绕过占用 |
| 多轮 grilling | 原题号、选项、自由文本与材料可读；多问题及分次答复整轮回送，等待期间未答项不默认同意 |
| 时效与错投 | 超时后有效续答仍回原任务；重复、错误引用、目标歧义、失效及原界面已答均不会重复执行或误投 |
| 执行审批 | 原生界面实际可达并定位正确任务；允许、拒绝与后续结果回流，规划确认不替代操作审批 |
| 工具与停止 | 每个开放入口在声明支持范围通过允许与拒绝测试；停止保留改动，确认结束才放行后续，未知范围保持占用 |
| 恢复与重排 | Gateway、插件或 worker 重载后核对既有工作，恢复监督或报告未知；原输入与工作不重复创建 |
| 身份与权限 | 真实 @ 与已核验身份生效，越职责请求拒绝，文本自称角色不提权，回声不产生新工作 |
| 交付与同步 | 总 Issue 验收、固定版本和真实测试齐备；PR 状态准确，涉及的本地与远端分支一致且用户内容保留 |
| 本机资料 | 日志和原生记录只有本人可访问；普通诊断和群消息不含凭据，公开产物不含真实绑定 |
| 插件生命周期 | 原 SDK 上加载、卸载和重载，关闭自有资源；全过程 SDK 源码字节不变 |

本机完整测试、双轴审查、Retro、Issue 存档与主工作区同步仍构成交付流程。远端 CI 是补充证据，不是本机个人使用的硬门禁。

## 范围之外

- 自建 Web Dashboard、专门聊天窗口、完整聊天镜像与完整组织配置界面。
- 完整资料迁移、长期档案管理与新的跨 Profile 原始记忆共享机制；独立助手的既有直接沟通入口保留。
- Desktop 手动会话观察或接管、旧运行任务迁移，以及对旧 18 张工单的原样补齐。
- 所有外部执行 MCP、自行脱离管理的后台服务，以及未经验证的全部执行入口或全系统进程终止保证。
- Codex 适配、跨主机执行端、通用跨平台部署和不属于本人 Mac 的运行支持。
- DSH 配套认证插件、认证 URL 导出、发布文件和导入器。
- 修改 Hermes、DSH 或第三方 SDK 源码，全局 monkey patch 或替换宿主 logger、信号处理。
- 未获具体计划授权的正式安装、长期启用、机器人变更或真实资料迁移。

## 补充说明

本文综合 2026-10-10 已确认的 Q1 至 Q10。责任层级、现有本地仓库绑定和合并后两层的能力保留，首版集中于实际开发流程。后续资料、界面与更广工具范围重新取舍，不默认成为第一项工作启动的前置条件。

当前实现可复用的部分包括原生插件入口、DSH 接入、仓库与输入对应、角色检查和证据验证；独立自动派发、逐票关联和广泛管理功能须按新范围取舍。现有单问题飞书入口、多问题回送、超时续答和原生审批访问存在已知差距，必须取得新验收证据。

原生 Kanban 派发 Hermes worker，DSH 托管仍由主插件接入。Mac 原生沙箱需实际配置与工具组合；原子进程范围实现不能保证所有逃离进程组的后代终止。原生 worker 输出会保存，静默显示与凭据脱敏不等于完全隐藏绑定，实际支持与权限以本机验证为准。

规格发布后添加 ready-for-agent。新实现工单依据本规格形成，旧规格、工单、PR 和测试只作为历史实现参考；正式启用仍按具体计划执行。
