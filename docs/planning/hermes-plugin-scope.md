# Hermes 分层协作与 Codex 监督插件：需求与范围记录

状态：需求与决定已收敛为[已确认首版规格](../specs/hermes-plugin-v1.md)。本文件保留需求来源和边界，不是已实现功能清单。

规范地图为 [Hermes 分层协作与 Codex 监督插件决策地图](https://github.com/Ghost233/GhostHermesProjectManagerPlugins/issues/1)。决定写入各工单解决评论，地图只维护索引；实现契约及通过标准见首版规格。

## 已确认的需求

### 责任角色与 Profile 分类

- 总管是通常沟通的入口，负责跨项目分配任务和汇总。
- 项目总负责人持有自己的 mono 仓库，通过 Codex 进行该仓库的开发、集成和全局测试，并管理自己下属的 Profile。
- 总负责人可更新 mono 仓库记录的子模块提交引用，不修改子仓源码或自行 checkout 子仓工作树；测试版本由子负责人或明确获准的准备动作提供。子负责人只完成明确分配的 GitHub Issue 中开发与测试任务。
- 子负责人由用户明确指定，不按 submodule 数量自动创建；每份子 Profile 长期绑定一个具体项目，本次任务完成后保留供同项目后续分配。
- 已指定子负责人全部交付后，总负责人再次执行全局验证。已分配子项目的缺陷以明确的 GitHub Issue 交回子负责人修复，再验证；未指定负责人的子模块问题交由用户决定。
- 项目总负责人和子项目负责人可合并，组织关系不要求固定三层；合并后同一 Profile 直接负责具体项目的开发与验证。
- 责任角色与开发型／非开发型 Profile 分开定义，不用层级强制决定能力。
- 开发型 Profile 向 Codex 发送提示词、监督会话并汇报，实际开发由 Codex 执行。
- 非开发型 Profile 可负责调度、资料或个人事务；这一分类本身不额外限制个人助手的通用工具。
- ConsoWiki、Ghost个人助手是独立助手，不放入项目责任层级。
- 总管管理全局组织目录；项目总负责人管理自己的下属，跨总负责人移交由总管处理。同一项目调整上级时保留子 Profile、记忆与历史。

### 创建、迁移、封存与恢复

- 为插件新建专用 Profile 和新飞书机器人，原 Profile 与原机器人停用归档。
- 迁移长期记忆、人设职责与通用偏好；模型与工具按新职责核对，Codex 执行配置由新插件重新配置。旧聊天历史保留为可查询归档，Wiki 保留原资料库连接。
- 新项目另建 Profile，不将原项目 Profile 改绑。恢复封存项目时继续使用原 Profile；恢复 mono 只恢复总负责人，子 Profile 逐个恢复，旧 Codex 执行需明确继续。
- 封存停止该项目范围的新任务，按既有控制授权立即请求中断执行并保留改动。只观察的手动执行须由用户明确处理或授权，不因封存自动接管；停止条件尚未满足时保持封存处理中和监督职责。
- 封存 mono 时总负责人及其所有子 Profile 一起封存，独立助手不随之封存。旧助手归档保留资料与历史，不自动删除或回滚代码。

### 公开协作与资料查询

- 设置总管入口群和各大项目群。总管参与入口与所有项目群；项目总负责人、子负责人留在对应项目群，独立助手按需要加入。交接使用真实 @，过程公开。
- 用户可以直接与总管、开发负责人、Wiki 或个人助手沟通。
- 开发负责人可以直接向 Wiki 请求资料，无需自己遍历大量资料库。
- 每项任务在各群建立对应起始消息，进展、问题和结果引用回复。插件保留跨群来源、目标、请求与上级关联，不要求用户输入技术编号。
- 简短回复能唯一关联时直接处理，多个候选时澄清，不默认最近任务。
- 子结果回项目总负责人，完成全局验证后回总管，总管在入口群汇总；用户直接给子负责人派任务时，答用户并同步总负责人。独立助手答实际提问者。
- 同一工作请求只受理一次，发送成功、受理和实际执行分别核对。“收到”“谢谢”和进度回复不产生新任务，不自动互相 @ 延伸工作。
- 第一期本人发起或控制开发和组织变更；登记机器人按授权职责协作，不冒充用户的新决定或审批。

### Codex 会话、控制与仓库排队

决定来源：[确定 Codex 会话登记、控制与接管规则](https://github.com/Ghost233/GhostHermesProjectManagerPlugins/issues/6#issuecomment-6019876234)。

- 首版只接入 Codex。
- 每次明确分派的工作建立独立 Codex 会话；同一工作的追加要求、停止和明确继续关联原会话，长期知识保存在 Profile。
- 插件任务按授权工作范围控制；自动发现已绑定项目仓库中的手动会话并默认只观察，无法确认的状态标为未知。
- 用户明确接管后，指定负责人在本次工作内持续控制；归还或本次工作完成后退为只观察。归还不打断正在运行的执行，状态冲突时停止相关自动控制并说明情况。
- 同一受管会话同时由一个指定负责人发出控制指令。接管须接入实际会话与执行服务，只读历史或另开执行器不能算接管成功。
- 同一逻辑仓库的外层任务串行排队，不同仓库可并行；Matt 内部并行继续由其工作流管理。可靠确认同仓库有只观察的手动执行时，新插件任务等待它结束或用户明确接管／处理。
- 普通交付核实原执行结束、固定交付证据并核对工作区后才释放占用。下一任务按自己的 Issue 和仓库约定确认基线，不默认承接上一未合并分支，不自动清理遗留改动或创建额外 worktree。
- 任务保留已受理目标、验收及可核实的 Issue 更新定位；运行中来源变化不静默扩大范围，新要求按明确追加或新请求处理。
- 停止结束当前外层任务并保留改动与会话。核实停止、报告遗留改动并核对仓库状态后，可处理后续队列；原任务不自动续跑，不自动回滚、关闭 Issue 或合并 PR，不自动 stash、移动、删除或覆盖用户文件。
- 明确继续已停止任务时，按新的执行安排关联原会话，并遵守当前仓库队列和控制归属。
- 重启或失联后先对账原会话及执行服务；仍在执行则恢复监控。只有确认执行已停止、任务未完成、原授权及范围有效，且没有主动停止或封存指令时，才自动继续原会话中的原任务；无法确认时暂停受影响的自动控制并请求用户处理，不重复启动。
- 全局验证期间暂缓相关仓库新的受管外层任务，核对稳定的父子版本组合；手动活动不自动干预，输入版本变化使本次验证失效。源码、Git 元数据和测试产物权限分别核对。

### Codex 监督与人工应答

决定来源：[确定监督状态、汇报频率与人工介入闭环](https://github.com/Ghost233/GhostHermesProjectManagerPlugins/issues/7#issuecomment-6020454695)。

- 按分配的 GitHub Issue 验收要求核对工作范围、约定测试、提交／PR 和遗留项；未要求合并的 Issue 可以交付，PR 待审查、待合并和已合并分别显示。Issue 明确要求合并时须完成合并。Codex 一轮结束不单独作为交付依据，未运行的测试不报告为通过。
- 总负责人自身工作及本次相关子 Issue 均满足要求、稳定父子组合上的全局验证通过后，才回传本次项目任务完成。
- 执行、控制归属、Issue 交付和 PR 状态分别核对。运行、有效待答／待批、可解释长命令、停止处理中和状态待核实分别说明；断连不等于执行停止，正在自行重试的错误不直接判为任务失败，权限或版本未就绪与代码缺陷分别报告。
- 有运行中或等待中任务时，总管每 15 分钟在入口群按项目汇总负责人、执行与交付状态、进展、阻塞、待处理事项及下一步；没有新进展也简短说明，无活动任务不发送定期消息。
- 子交付与返工在项目群即时回传；本次项目任务完成、停止确认、封存完成或需要用户处理的受阻情况，单独更新一次。普通结果不额外 @，重复事件不产生新的重复告警，恢复后不补刷停机期间每个定时消息。
- 能确认仍在执行、排除明确等待和可解释长命令后，连续 15 分钟无可核实进展时核查；仍无法解释才通知疑似停滞，不据此自动中断、重启或另开执行。
- 监督通道失联先说明执行待核实并重连对账，持续 2 分钟未恢复则通知，恢复后更新一次；通知依赖监督组件运行及通道可用，自动继续仍遵守既定对账条件。
- 需要本人审批的操作和阻塞执行且需要本人回答的问题，由总管立即在入口群 @ 用户；非阻塞普通问题随汇总。有效且仍需本人处理的审批或阻塞问题每 30 分钟再次 @，失效或解决后停止提醒；未答复不默认批准、拒绝、停止或取消。
- 已授权控制的负责人可在既有资料权限内，注明来源后答复已定规则及可核实事实；新需求、方案取舍、操作授权、明确要求本人回答或无法核实的问题交用户。Wiki 与跨 Profile 的共享遵守下述资料规则。
- 入口群或项目群的答复须唯一关联原请求；审批还须由已核验的本人明确表达针对具体操作的批准／拒绝或原请求支持的有效决定，普通“继续”“好的”不自动当作批准，不从简短答复扩大授权。
- 回送前核对原请求有效性、答复者身份及控制权限；同一请求的一次有效答复只受理一次，过期或重复答复不触发新执行，结果不明先对账。只观察或归还控制后不回送，需到原会话处理或先明确接管；不缓存旧批准待以后执行。
- 分别说明已收到答复、已送回原请求、请求已处理和后续执行结果；请求已处理不等于操作成功。重连历史不能替代仍有效的人工请求，无法核实时到原会话处理。
- 敏感问题在群内仅通知处理入口及可核实的任务定位，敏感答案到原 Codex 界面处理，不复制秘密到群消息或插件记录；脱敏后不足以判断的审批也到原界面审阅。
- 本轮全局验证通过、失败或因输入版本变化失效后，结束本轮验证占用；任务未因此自动完成，子缺陷以明确 Issue 交回修复后重新核对稳定组合并验证。停止尚未核实时不能释放仓库队列或报告封存完成。

### 资料查询、任务上下文与记忆回写

决定来源：[确定资料查询、上下文传递与记忆回写边界](https://github.com/Ghost233/GhostHermesProjectManagerPlugins/issues/8#issuecomment-6021181667)。

- 通过公开真实 @ 请求共享与任务相关的资料、摘要和来源；目录管理及上下级关系不自动开放其他 Profile 的全部原始记忆和历史，额外直接读取须本人明确授权。
- 资料来源登记其可查询及可公开共享范围，范围内的正常请求无需逐次批准；回复和送入 Codex 前核对当前请求、项目及共享范围，加入群不开放全部私人资料。
- Wiki 请求标明项目／Issue、问题、相关版本或时间条件及约束；默认返回简洁结论、必要材料和来源，提供可取得的版本／时间，区分事实、推断、建议、冲突及过期资料。未查到或无权限时说明实际范围，不以猜测补作确定事实。
- 开发成果保存在项目 Issue、仓库和所属 Profile 记忆，开发流程不自动改写 Wiki 原资料库；由本人明确要求 Wiki 整理维护时核对目标与内容，写入能力按实际连接验收。原资料库连接保留，Wiki 记忆与原资料库分别保管。
- 新 Profile 在已登记允许范围内，只读查询自身迁移来源的旧档案；其他旧来源需授权，上级默认公开 @ 对应负责人查询并回传相关材料。查询不恢复旧 Profile、机器人或 Codex 执行。
- 项目及负责人封存后，本人在入口群公开 @ 总管，由总管按本人登记的档案查询及公开共享范围只读代查，回传相关结论与来源。范围内不逐次批准，超范围再明确授权，不恢复旧入口。
- Hermes 本地档案、飞书群历史与 Codex 历史分别标明来源；默认按问题检索补读，明确要求完整会话时覆盖必要分页和压缩历史，读不全须说明范围。登记旧档案与封存 Profile 资料永久保护，备份及恢复按已确认规格验收。
- Codex 上下文围绕当前 Issue 的目标、验收、仓库写入边界、已定决定、约束和必要事实材料；不默认附带全部记忆或跨项目私人历史。链接不可访问时补充允许共享的实际相关材料，不用不可访问链接代替必要上下文。
- 保留 Codex 原生配置、仓库规则和 Matt 工作流；资料或历史中的指令不自动成为本人新要求或审批。新材料只送入已授权的实际任务会话，只观察、任务结束或归还控制后不发送输入，迟到材料不自动启动执行。
- 子负责人保存绑定项目事实与交付索引，总负责人保存自己的 mono、协调与全局验证资料，总管保存目录、跨项目汇总及本人明确指定的共用约定；各角色回写自己的记忆，上级保存必要协调摘要，不合并全部下属原始记忆。
- Issue 验收交付后自动提炼本项目的已验收事实、已确认决定、测试／PR 索引及来源，记录实际对应版本和可核实时间；不复制全部日志，也不把临时状态、未证实推断、未处理审批或秘密写为长期事实。
- 偏好仅依据本人明确表达与适用范围更新，一次方案选择不推广为所有项目的永久偏好；明确纠正或新证据使旧摘要不适用时更新精选记忆并标明替代关系，不自动改写原资料或历史。
- 记忆更新不等于正在运行的会话已加载新内容，影响当前任务须遵守有效控制关系；新项目新 Profile，封存与恢复保留原绑定，调整上级不复制全部原始档案。独立助手保留自身职责，个人事务不自动成为项目公共资料。
- 查询来源范围、普通工具调用、旧档案完整读取及记忆实际加载仍需验收，不能因原生跨 Profile 查询可用就默认开放所有来源。

### 工作流与已有环境

- 开发沿用 Codex 的原生配置、仓库约定、Matt Skills 和 GitHub Issue／PR。
- Hermes 监督执行，不重新建立一套 Matt 工单拆分或内部开发流程。
- 使用现有本地仓库；只有用户明确要求时才 clone。
- 项目资料随其长期绑定的子 Profile 保留，总负责人保管自己的协调资料；各层公开共享所需材料，验收后回写所属角色的精选记忆。
- 通过插件统一管理角色和执行监督；迁移、历史保留、安装升级与兼容验收遵循已确认首版规格。

### 管理与实现交接

- 飞书聊天与 Hermes Web Dashboard 共用规则、权限及状态；新机器人开通和必要凭据录入保留人工步骤。
- 首版 Hermes 管理与 Codex 执行端同机，Wiki 可沿用已授权的外部资料连接；首版不提供跨主机 Codex 执行端。
- 一个管理实例使用独立 SQLite 保存全局目录、队列与关联凭据，各 Profile 保留自己的记忆和原生存储。
- 登记旧档案和封存资料永久保护；变更前建立一致性检查点，变化数据每日快照保留最近 7 个，检查点及可恢复档案基线长期保留。
- 升级先维护并核对交接点；主动停用停止接新任务、中断并核实受管执行，只观察手动会话不自动中断。具体配置、接口与验收契约见首版规格。

## 需求对应的验收场景

1. 一个项目采用三层负责人且总负责人有自己的 mono 执行，另一个项目合并后两层；只为明确指定的项目建立子负责人，独立助手仍可直接联系。
2. 开发负责人在群内真实 @ Wiki，获得有来源、可取得版本／时间的相关答案，区分事实、推断及冲突；仅将允许共享的必要材料送入 Codex，不自动写 Wiki。
3. 同一群有两项并行执行，进展、问题和答复能关联到正确任务，重复消息不重复启动开发。
4. 自动发现手动会话并只观察；接管限本次工作并核对实际控制归属，归还不打断执行，同仓库新任务等待已有手动执行结束或用户明确处理。
5. 区分长命令、有效待答／待批、通道失联和疑似停滞；群内答复核对身份、控制权限和原请求有效性，重复或过期答复不重复执行，普通继续不代替审批。
6. 插件或 Gateway 重载／重启后对账已有任务；执行中只恢复监控，符合条件才自动继续原任务，未知状态不重复启动，主动停止或封存任务不自动续跑。
7. 按 Issue 验收证据确认交付，分别报告固定交付版本、PR、测试、审查和同步；普通交付核对工作区再交接下一任务，Issue 后续修改不自动成为原范围。
8. 子 Issue 交付后由获准动作准备测试版本，总负责人更新子模块引用而不 checkout 子仓；全局验证期间相关新任务等待，父子版本变化使验证失效；本轮验证结束释放占用，缺陷沿 Issue 交回，修复后重新验证。
9. 新 Profile 与新机器人迁移知识和偏好，旧历史保持可查询；mono 与下属一起封存，只观察的手动执行仍需用户明确处理；恢复总负责人后下属逐个恢复，原绑定保留。
10. 停止结束外层任务、保留已有改动；核实停止和仓库状态后才处理后续队列，明确继续关联原会话，不自动覆盖遗留内容。
11. 有活动任务每 15 分钟汇总；15 分钟无可解释进展后核查、持续失联 2 分钟后通知、有效待答请求每 30 分钟再次 @；明确等待和长命令不误判，无活动不定期刷屏，组件停机后先对账再汇报。
12. 敏感问题群内仅通知定位，原界面处理敏感答案；未经证实有效的旧请求或旧批准不在恢复后自动执行。
13. 已授权负责人能依据允许共享的已定规则和有来源资料答复普通问题；新决定交本人，只观察的会话不发送答复。
14. 新 Profile 只读查询登记的自身旧来源；父子全部封存后由总管按登记范围代查，超范围须授权。完整会话涵盖必要压缩／分页历史，无法完整读取时标明范围，查询不恢复旧入口。
15. 项目验收后各角色保存自己的精选事实与结果索引，偏好按本人明确范围更新；新证据纠正旧摘要，上级协调不合并下属全部原始记忆。
16. 资料或记忆更新不静默改变当前任务权限，迟到材料不启动旧任务；不可访问链接补充允许共享的必要材料，秘密不进入公开回复和项目长期事实。

具体预期输出、离线与真实环境通过标准已收敛于首版规格的验收矩阵，当前没有声称已通过这些场景。
