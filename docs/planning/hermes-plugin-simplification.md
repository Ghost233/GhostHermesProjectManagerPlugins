# Hermes 开发协作插件简化方案

状态：2026-10-10 的 Q1 至 Q10 已确认，用户已调用 to-spec 并确认公共测试接缝。当前实现契约见[简化首版规格](../specs/hermes-development-coordination-v2.md)。生产代码尚未按新方案重构，旧测试结果不作为新方案通过的证据。

## 首版目标

在个人 Mac 上，从飞书发起一项明确开发工作，由仓库负责人监督 DSH 按 Matt 完成规划、实施、测试和审查，最后按 GitHub Issue 验收并汇报。先验证一个仓库，再验证不同仓库的并行派发及必要协调。

总管接收需求、分配仓库级工作并汇总。项目总负责人可以继续协调下属；有自己的仓库才承担该仓库的开发或验证。没有仓库的调度负责人只派发和汇总，不自动创建 mono 仓库。

已有负责人层级和本地仓库绑定继续作为项目配置。各层内部交接，用户仍可直接 @ 负责人或独立助手。首版保留必要绑定，完整组织管理界面与资料功能留到后续重新取舍。

## 职责分工

| 角色或组件 | 职责 |
| --- | --- |
| Hermes 总管 | 接收需求、派发完整工作、汇总关键事件与需要用户处理的问题 |
| 原生 Kanban | 唯一的外层任务队列，记录负责人、依赖和运行状态 |
| 仓库负责人 | 监督本仓库 DSH 工作、转交原问题、核对交付并汇报 |
| 专用 DSH | 在本仓库按 Matt 详细拆分、实施、测试和审查 |
| Hermes 主插件 | 补充本地仓库互斥、DSH 接入、原任务答复与验收，不另设自动派发队列 |
| GitHub | 保存总 Issue、细任务 Issue、验收说明和 PR |

Kanban 的内置自动拆分停用。Hermes 不逐票重做 DSH 的 Matt 调度，也不把 DSH 的完整聊天复制到飞书。

## 开发流程

1. 用户提出需求或指定已有 Issue，负责人确认目标仓库与工作范围。
2. 每个仓库的完整工作对应一个总 Issue 和一张外层任务卡。同一逻辑仓库的外层任务串行，不同仓库可以并行。
3. 负责人使用该项目的专用 DSH 实例，为本次工作建立独立会话。DSH 按 Matt 细拆，细任务 Issue 留在 GitHub，不再逐张建立 Kanban 卡。
4. 负责人监督状态并转交人工问题。飞书展示关键交接、需求分歧、接口变更、阻塞与交付结果。
5. DSH 完成后，负责人依据总 Issue 核对范围、实际测试、固定交付版本、PR 和遗留项，再报告交付。一次模型回复结束或一张卡显示完成，均不能单独证明交付。
6. 需要跨仓库验证时，由明确指定且具有相应仓库的负责人承接测试工作。调度负责人汇总结果；不自行修改其他仓库或为测试自动创建新仓库。

首版沿用已确认的约定：PR 审查和合并状态分别报告；只有任务明确要求且具有授权时才合并。远端更新后同步对应本地分支，只允许 fast-forward，不自动 stash、移动、删除或覆盖用户内容。

## 飞书问答

DSH 主持 grilling，负责人转交原问题。每轮用一条提问消息呈现，保留题号、选项和必要上下文，指明任务与总 Issue。需要确认方案时提供可读材料或受限附件，不能只给用户无法打开的本机路径。

用户引用本轮消息，并通过平台选择器真实 @ 发问机器人，用题号或自由文本回复。允许分次回答；负责人记录已答和待答项，收齐后整轮送回同一 DSH 任务。明确跳过或交给 DSH 决定时，保留用户的原答复，未答题目不自动当作同意。

来源不能唯一确定时先澄清。重复、失效或已处理的答复不再触发执行。普通文字提问按原会话对话继续，结构化提问按原请求回应；不把普通输入冒充执行审批。超时后仍有效的续答须走原生支持路径，不因旧传输关闭就自动丢弃，也不盲重发。

普通问答和规划确认在飞书处理。具体执行审批到本机 DSH 原生界面确认，群里只通知必要定位；原生界面可达性、正确任务定位与结果回流必须实测。敏感值不在群里提交，也不复制到插件记录。

## 首版运行范围

只管理 Hermes 为项目创建的专用 DSH 实例和任务。Desktop 手动会话观察与接管、外部执行 MCP 和自行脱离管理的后台服务留到后续。

只开放经过真实测试的原生开发工具及后台任务。按工具实际能力验证本仓库写入、越界拒绝与停止结果，目录绑定或权限模式名称不能替代证据。停止范围不明时报告未知，保留当前仓库占用并暂停后续派发。

停止保留改动，确认停止与仓库状态后再处理后续任务。重启先核对原 DSH 会话及工作；恢复监督，不重复创建任务或重送未知输入，主动停止的工作不自动继续。原生 Kanban worker 重排也须复用或核对已有 DSH 工作。

不修改 Hermes、DSH 或第三方 SDK 源码。平台、工具、Hook、后台任务与卸载使用原生接口；不全局替换 logger 或信号处理，不恢复认证 URL 导出、发布文件、导入器或配套认证插件。

## 通知与记录

首版沿用已有通知约定：有活动工作时每 15 分钟汇总；需要用户处理的阻塞问题、执行审批和交付结果及时通知。明确等待不误报卡死，重复事件不重复告警，无活动任务不定时刷屏。

原生任务和会话记录保存在受限本机。原生日志可包含非秘密项目名称、路径等运行信息，目录与文件实际权限须核验。凭据不得进入普通诊断日志、群消息或公开产物。

群通知只包含允许分享的内容，完整聊天不自动同步。插件源码、测试、版本化文档和公开 Issue／PR 继续使用合成引用；必要真实绑定从仓库外受限配置注入。

## 首版验收

| 场景 | 必须取得的证据 |
| --- | --- |
| 单仓开发 | 飞书受理、唯一外层卡、正确本地仓库、原 DSH 会话、细 Issue、真实开发测试和交付版本 |
| 多轮 grilling | 多问题、分次收集、自由文本、超时后有效续答均回到正确任务；重复、错投、失效和原界面已答情况正确处理 |
| 执行审批 | 本机原生界面能打开正确任务，允许或拒绝后真实结果回流，规划确认不代作执行许可 |
| 仓库协调 | 同仓串行、不同仓可并行，worker 重排与未知输入均不重复启动 DSH |
| 工具与停止 | 每个开放入口在支持范围内通过正反测试；停止保留改动，范围未知时不释放占用 |
| 身份与权限 | 真实 @、本人身份、登记职责和工作范围生效，文本自称身份或角色不提权 |
| 本机资料 | 实际目录、文件和日志采集受限，凭据不进入普通诊断或群消息，公开产物不含真实绑定 |
| 插件生命周期 | 未修改 SDK 上加载、卸载和重载；自有资源清理、重启核对与源码字节不变 |

本机完整测试、双轴审查、Retro、Issue 存档和本地主工作区同步仍是交付流程。真实模型、飞书与 DSH 往返分别取得证据，不能用合成测试或旧方案的通过数量代替。正式安装与长期启用仍按具体计划执行。

## 暂不纳入首版

自建 Web Dashboard、完整聊天镜像、完整组织配置界面、资料迁移与长期档案管理、Desktop 手动接管、所有外部执行 MCP 与脱管后台服务。用户确认当前没有残留运行任务，旧实现可按新范围替换，旧 18 张工单不作为新首版必须原样补齐的清单。
