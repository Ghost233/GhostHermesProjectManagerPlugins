# Feishu Issue intake slice ([从飞书群受理 Issue 并公开确认关联](../../../../issues/15))

This slice implements acceptance only. It never creates a Codex session, reports a task as running, edits an Issue, or starts a second manager. `Manager.accept_request` freezes the Issue URL, title, body and `updated_at` obtained at acceptance. A repeated source event keeps that original scope. `read_snapshot` returns the same requests, delivery ledgers and clarifications to native participant readers and Dashboard through the existing private bridge. Dashboard shows acceptance, message delivery, the original/local start anchors and the reason execution is waiting.

The public message syntax is a **real Feishu mention of the registered responsible bot**, followed by `派发 https://github.com/OWNER/REPO/issues/NUMBER`. A display name, literal `@Name`, a mention hint in normalized text, another app's IDs or an unverified sender cannot authorize intake. The Issue repository must exactly match the trusted binding. GitHub reads switch to the account resolved from the protected native configuration, verify the effective login (including token overrides), then read only `url,title,body,updatedAt`. Failures do not create acceptance evidence. An explicit Issue URL without the `派发` verb does not create new work.

Production ingress uses formal `register_platform(name="hermes_feishu_pm", ...)` and a plugin-owned `OwnedFeishuAdapter` based on `BasePlatformAdapter`. The plugin owns receive parsing, sender and mention checks, original-message dispatch and durable dedup. It does not enter the builtin Feishu adapter's receive chain, which logs information before a plugin consumer can inspect it. Native `pre_gateway_dispatch` only boots the management authority. Tools, hooks, background tasks and unload use the SDK's existing registration interfaces; Hermes source stays unchanged.

The owned entry inspects the raw original, exact transport pairing and target first; then calls `_is_user_authorized_for_source(original_source)` in its native authorization home and verifies the paired bot identity. It checks the registered target's actual routed runtime Profile before native bot admission. Only explicit successful admission creates a process-local commitment bound to the original event/source. That committed original never enters native batching/busy flow even if business processing declines or throws. Failure remains unaccepted or needs reconciliation, with a bounded reason and separately recorded safe notification. Unauthorized originals are rejected without falling through to native dispatch. Ordinary non-candidate input retains native conversation handling; its host logging is a separate privacy gate. Business processing uses the actual pinned runtime home without rewriting source identity to borrow privileges.

Compatibility tests use unmodified Hermes `bd0affe5e5f723579df8902852f5d0c47795f355` and `lark-oapi==1.6.8`. The runtime has no dependency on a patched SDK hash or a host privacy helper. `intake_conditions` reports native platform registration, the explicit allowlist and same-app policy, while real connection and group acceptance remain separate gates. A source upgrade requires another actual ingress, authorization and lifecycle acceptance run.

Raw SDK `P2ImMessageReceiveV1` header, sender and mention identities are checked independently. Header app/tenant, sender tenant and recipient mention tenant are separate facts; Feishu does not promise all three tenants are equal. The runtime Profile is not used as app identity. The captured native client's public `config` must establish the supported automatic SELF token path, and the formal bot-info request must return valid JSON with `activate_status=2` and the exact expected `bot.open_id`. Manual-token and ISV paths remain unsupported. No config object, token, raw SDK event or raw error response is persisted. Known resolved bridge secrets, captured client app secrets and recognizable credential/private-key material are rejected before acceptance or public message storage; sensitive answers belong in the original private interface. This is a bounded public-material policy, not a promise to recognize every arbitrary secret string.

Trusted settings add this **synthetic shape**, with `enabled` remaining false by default:

```yaml
feishu_intake:
  enabled: false
  verification_ref: evidence:approved-test-intake-plan
  bindings:
    - project_id: fixture-project
      profile_id: fixture-lead
      repository: fixture-owner/fixture
      app_id: cli_fixture
      recipient_open_id: ou_fixture_bot
      owner_open_id: ou_fixture_owner
      owner_native_ids: [u_fixture_owner, on_fixture_owner]
      chat_id: oc_fixture_project
      transport_tenant_key: fixture_receiving_tenant
      sender_tenant_key: fixture_owner_tenant
      recipient_tenant_key: fixture_bot_tenant
      verification_ref: evidence:verified-identity-map
  registered_bots: []
```

The owner-approved binding is an identity mapping reference; it does not itself prove real-message delivery, full incoming-message coverage or production readiness. IDs must come from the approved app/sender/tenant namespaces. The management Profile must own the authority, and the registered target must be a development Profile of the specified project. No bot, Profile, app, group, credential or repository is created by these settings. This turn supplied no real test-group or credential references; no real connection is enabled.

Enable the independent platform name only in an approved new native Profile's platform configuration with explicit native app credentials. The owned constructor does not fall back to old `FEISHU_APP_ID/SECRET`. It checks `owner_native_ids` and explicit registered-bot IDs, and registers `HERMES_PM_FEISHU_ALLOWED_USERS` as its allowlist namespace with no allow-all metadata. Native transport restrictions still apply and cannot be overridden by a plugin role claim. Provisioning must configure the exact verified ID range. The plugin also independently rejects principals outside that range before processing raw events.

A registered bot entry is `{profile_id,identity_ref,app_id,tenant_key,open_id,native_ids}`. It must match a registered Profile and its current project responsibility for that chat. The actual source stays `is_bot=true`; configured bot and native group policies still apply, and Gateway bot limits still charge native bot traffic. Unknown bots and owner-ID bot impersonations are rejected. Bot-authored development requests require the distinct role-based collaboration entry. No IDs are inferred by display name.

Feishu I/O runs in a plugin-owned child process, with a private inherited socket for events and RPC. The child receives only its app credentials through IPC and a minimal runtime environment; credentials are absent from argv and console. Its own diagnostic output is suppressed without changing any host logger, record factory or signal handler. The parent attaches the corresponding transport after connection succeeds. Reconnect replaces that pairing; disconnect removes it. Unload invalidates the intake generation, closes the plugin process and socket, cancels its tasks and releases the same-app lease. Identity checks, Issue reads, queued processing and send boundaries recheck lifecycle before further effects. Already-issued external requests retain unknown receipts on interruption. The driver rejects a configured builtin or owned driver for the same app. Actual shared ingress and live shutdown still require real-environment evidence.

## Log privacy boundary

Plugin intake and Feishu child diagnostics must not persist raw messages, identifiers or credentials. The child isolation does not guarantee ordinary native conversation logs or host startup, shutdown and error diagnostics. A bounded probe of unmodified `setup_logging` with `logging.level: CRITICAL` still wrote a synthetic warning marker to two ordinary log files, while all 8,014 Python source files stayed unchanged. That configuration alone is insufficient. Deployment must demonstrate an allowed configuration or isolation boundary for the remaining host paths before privacy acceptance; no global logging, signal or SDK rewrite is an available workaround.

Bridge snapshots now use an eight-byte unsigned network-order byte length and complete bounded-chunk reads. Requests retain their explicit 1 MiB bound; responses consume the complete authority frame rather than truncating legitimate scopes/outbox records. Both client and server must use this plugin revision; no material is deleted or mislabeled offline to fit transport. Request IDs/association include the verified app and all tenant namespaces. Explicit parent/start quotes take precedence over common root/thread fallback. Adding pending segments and claiming sending segments update the aggregate immediately; a restarted authority exposes sends it no longer owns as unknown and forbids automatic replay.

`publish_request_message` persists an outbox before sending. The short confirmation becomes the local task start anchor only when its returned message ID and actual chat are known. Long material is split into bounded logical segments; each segment has its own persistent UUID, number, attempts, intended reply anchor and scalar response receipt. The captured client uses the **formal** `ReplyMessageRequest`/`ReplyMessageRequestBody` builders with a post `at` element and that segment's UUID. It does not rely on adapter `.send`'s last-chunk result or private retry/fallback behavior. Missing message IDs/chats, exceptions and interrupted in-flight sends remain unknown. Actual root/parent/thread fields remain null if the response does not supply them; no message URL or quoted relationship is invented. A normal root quote remains distinct from native `thread_id`.

Only definite API failures can be retried. In the same verified group/app/sender scope, the owner can send `重试投递 FULL_REQUEST_ID` (the ID is shown on Dashboard). It reuses failed segment UUIDs, preserves successful segments and the original anchor, and resumes later pending segments. Duplicate request delivery does not retry failures by itself. Unknown delivery rejects retry until reconciliation; this slice deliberately has no speculative reconciliation or automatic replay operation.

Failure notifications have their own durable initial-send claim keyed by the same verified app/tenant/sender/recipient/chat namespace and message ID as request acceptance. Optional root/parent/thread locator changes cannot create another notice claim. Lookup preserves existing failure IDs, notification UUIDs and frozen source locators from earlier envelope-keyed records. Existing unknown, delivered or failed failure notices are never resent by original-event replay, even after bounded native dedup/commit cache eviction. Such replay is also stopped before another admission charge. A failure notice has no automatic retry or reconciliation command in this slice; a new explicit request is separate from replaying the old original. No SDK UUID retention window is treated as permanent delivery proof.

Issue reading has the same worker-start generation fence as identity/send: a queued executor job checks lifecycle before beginning the external GitHub reader, then the async caller checks it again after completion. A read already issued before close remains an external in-flight operation; queued reads are not allowed to start after unload.

Ordinary owner input associates with one request by source/confirmed anchor or by a unique candidate in the same group, app and responsibility scope. Multiple candidates produce a persisted clarification and a reply asking for the task start quote. They do not choose the latest task. `收到`, `谢谢`, `好的`, `ok` and `thanks` terminate the reply chain. Progress/result inputs are associated observations, not new work or proof that Codex executed. They preserve accepted scope and waiting execution. `publish_request_message` supports progress/result output at the same public management seam and uses the same local start anchor.

## Isolated verification

Install the test extra in a disposable development environment. It pins `lark-oapi==1.6.8`, the version in the fixed Hermes SDK. Run:

```sh
HERMES_TEST_SDK_ROOT=/tmp/pristine-hermes-sdk \
HERMES_REQUIRE_SDK_SMOKE=1 python -m pytest -q
node --check dashboard/dist/index.js
```

Tests use public management operations and the native entry/transport boundary. They never manufacture state by writing SQLite or invoking Manager private methods. Native smoke loads the unmodified SDK directly, with temporary plugin installations and artificial homes. It exercises PluginManager loading, hooks, the platform factory, native event/source types, Dashboard and the private bridge. Complete SDK source snapshots must match before and after load, receive/send, refusal, unload and reload. External network and Issue services use controlled substitutes; production profiles and network calls are excluded. Long-message segments, genuine `at` request shape, duplicate delivery and same-authority snapshots retain their business assertions. Passing this smoke is **not real Feishu acceptance**.

## Approved real-group smoke and outstanding gates

The executable isolated smoke is `tests/test_native_runtime.py`. For real acceptance, use an explicitly approved **test-only** management Profile, target development Profile, app, group and fixture Issue. Keep production `enabled=false`. Before any test-only enablement, obtain the non-sensitive native Profile/state-directory references, project/Profile IDs, exact GitHub repository/Issue and expected update time, app/bot/owner IDs, the three independently verified tenant references, allowed group ID and native credential **references**. Credentials stay in native secret storage. Record the allowed test plan and identity-map evidence refs. Verify existing native group/admission policy rather than weakening it. No real service installation or configuration changes are authorized by this development document.

1. In the approved inactive test lane, have the actual owner use Feishu's mention picker to address the actual registered bot and send the exact `派发 ISSUE_URL` command. Verify the resulting actual `at`, source/app identity, public short confirmation and each long-material reply in the group. Match original/source IDs and returned local start IDs to Dashboard. Confirm `acceptance=accepted`, `execution=waiting`, `delivery=delivered` only when every segment has a distinct recorded receipt. The actual group observation is required in addition to a successful send response.
2. Redeliver the same original event using the approved test harness's event replay path, without creating a new message ID. Confirm one accepted request and no duplicate successful segment. Where the approved harness can produce a definite failed API response, use `重试投递 FULL_REQUEST_ID`, then verify only failed/pending segments are sent. Do not replay a timeout/unknown delivery as if it were a definite rejection.
3. Quote the actual start confirmation and send progress/result input; verify association and the original anchor, then send `谢谢` and confirm no new work/reply chain. Create a second explicitly separate fixture request; ordinary ambiguous input must ask for a quote. Verify foreign app/tenant/sender, a display-only mention, missing identity evidence and unauthorized source never receive plugin confirmation or acceptance.
4. Restart only the approved test instance and verify the same frozen scope, receipts and pending reasons. Preserve unknown sends. Export the authenticated Dashboard snapshot as evidence without credentials and run `python tools/check_feishu_acceptance.py SNAPSHOT.json --chat-id CHAT_ID --source-message-id SOURCE_ID --start-message-id START_ID --issue-url ISSUE_URL`. This validates the exported record's structure against observed IDs; it does not authenticate the export or replace group observations.
5. In the approved new platform, test rapid independent TEXT requests and a request while a native agent is active. They must reach the owned prebatch consumer individually with original raw/source IDs, while ordinary non-candidate traffic follows native debounce/busy handling. Verify denied/unknown authorization and disabled bots/groups never create acceptance, source failures after admission cannot fall back or re-charge, and reconnect binds the current actual client under the correct transport/routed runtime homes. Repeat with the exact new native allowlist; do not reuse old builtin bot bypass assumptions.

No real group smoke has run. Production installation, live connect/shared ingress/shutdown and Codex execution remain unverified/not enabled. The actual SDK owned route now has isolated per-original rapid/busy/admission evidence, but the independent feasibility probe is not production acceptance. **[从飞书群受理 Issue 并公开确认关联](../../../../issues/15) complete runtime acceptance remains open until the approved real group and connection gates pass.**

The plugin uses its own registered platform to consume task candidates before native conversation batching. Neither a new host ingress hook nor a host privacy patch is part of this implementation. The unchanged SDK must still pass the actual platform, authorization and lifecycle tests, and remaining native logging limits stay explicit acceptance gaps.
