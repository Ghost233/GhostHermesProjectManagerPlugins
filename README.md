# Hermes 个人项目管理插件

通过飞书协调本地仓库开发，复用 Hermes 原生 Kanban 和当前 DSH Desktop 后端。插件仅供本人在 Mac 上使用。

## 安装与开始使用

已经完成配置的 Profile，可以直接从“在飞书发起工作”开始。以下项目名、Profile 名和仓库地址均为示例，请替换成自己的登记信息。

### 安装到 Hermes Profile

先启动平时使用的 DSH Desktop，并确认 Hermes、飞书机器人和 GitHub 账号可用。总管与仓库负责人分别使用自己的 Hermes Profile；总管可以只负责派发，仓库负责人绑定本地仓库根目录。

从本仓库 GitHub 页面复制仓库地址，再用 Hermes 原生安装器安装到指定 Profile：

```bash
PLUGIN_SOURCE='替换为本仓库的 GitHub URL'
hermes -p example-manager plugins install "$PLUGIN_SOURCE" --no-enable
hermes -p example-dev plugins install "$PLUGIN_SOURCE" --no-enable
```

按安装器提示核对依赖和权限。安装代码不会自动创建飞书应用、登记项目或配置 DSH 接入。启用前，在各 Profile 的 `config.yaml` 中配置 `plugins.entries.ghost-hermes-pm.settings`，并准备以下绑定：

| 配置内容 | 需要确认的事项 |
|---|---|
| 本人和飞书入口 | 本人身份、机器人、群、真实 @ 收件和审批卡回调已核验；凭据保存在本机受限配置中 |
| 总管与仓库负责人 | 明确各 Profile 的职责、允许派发的对象和项目范围 |
| 本地项目 | 登记 GitHub 仓库及对应本地根目录；只有远端地址不足以执行开发 |
| Issue 创建 | 允许从需求创建总 Issue 时，给对应负责人配置 `issue_creation_allowed: true`；否则派发现有 Issue |
| 原生派发 | 显式启用 `simple_development`，复用当前 Hermes Kanban，并关闭 `kanban.auto_decompose` |
| 当前 DSH | 使用现有 Desktop 后端和原生认证；主包 Hook 已加载，模型、工具与请求预算已配置 |
| 插件状态 | 使用仓库外受限状态目录，保留任务、会话、问题、审批和用量记录 |

这些绑定包含本机身份和执行权限，不能直接从其他 Profile 复制一份就视为配置完成。接入约束见[当前规格](docs/specs/hermes-development-coordination-v2.md)和[同实例接入决定](docs/adr/0002-dsh-led-repository-work.md)。

完成配置后启用，并检查安装状态：

```bash
hermes -p example-manager plugins enable ghost-hermes-pm --no-allow-tool-override
hermes -p example-dev plugins enable ghost-hermes-pm --no-allow-tool-override
hermes -p example-manager plugins list
hermes -p example-dev plugins list
```

如果当前 Gateway 已运行，使用它现有的按 Profile 重载入口加载这两个 Profile。再核对实际工具、收件和 Hook 状态。安装列表显示启用，不代表原 DSH 会话已加载新版 Hook；需要维护时先核对活动工作，保留原会话和账本。

### 从 GitHub 更新

普通安装跟随本仓库默认分支，不需要指定版本号或提交 SHA。对每个已安装的 Profile 分别更新：

```bash
hermes -p example-manager plugins update ghost-hermes-pm
hermes -p example-dev plugins update ghost-hermes-pm
```

更新前备份配置和状态，更新后核对实际加载。已有固定提交安装需要先恢复为普通 GitHub 安装，才能使用上述更新命令。遇到安装器告警时先核对来源、差异和作用范围，不把 `--force` 当作默认步骤。

### 在飞书发起工作

在已登记群中，用飞书的 @ 选择器选中总管。先说清目标项目、需求、验收条件和禁止事项；Hermes 有疑问时会继续问你。新项目需要先登记本地仓库与负责人。

例如，向“示例总管”发送以下消息。`example-dev` 是已登记仓库负责人的 Profile 标识：

```text
@示例总管
工作 example-dev 商品列表页面
在已登记的示例项目中实现商品列表，支持关键词搜索和空结果提示。
请先和我确认需求，再拆分任务。完成后运行实际测试并创建 PR，暂不合并。
```

已有 GitHub Issue 时，可以直接派发：

```text
@示例总管 派发 example-dev https://github.com/example/sample-app/issues/1
```

收到受理回复后，核对项目、总 Issue 和工作引用。随后在当前 Hermes Kanban 中查看外层卡，在现有 DSH 的对应项目工作区打开会话。受理和排队只表示请求已登记，实际提示词、开发和测试进展以原会话及群内结果为准。

### 回答问题、审批和查看进度

普通问题请引用发问消息，真实 @ 发问机器人，再回答 `Q1`、`Q2` 或自由文本。分次回答也可以；多个任务并行时，保留问题编号和工作引用，避免答到另一项工作。

具体执行审批在原卡片上选择“批准一次”或“拒绝”。决定送达与工具执行结束分别显示。`/new` 的确认卡属于 Hermes 对话重置；其中“始终批准”会持久改变后续确认设置，请先阅读卡片说明。

活动工作每 5 分钟或新增 10 次 DSH 请求检查一次，先到者触发。Hermes 决定是否立即回传；阻塞问题、审批和交付会及时通知。你也可以真实 @ 总管询问某项工作的进展。

需要明确定位时，将下面的 `<工作引用>` 替换成受理回复中的完整引用：

```text
@示例总管 核对 <工作引用>
@示例总管 停止 <工作引用>
```

停止保留已有代码和历史，是否完成停止以核验结果为准。请求预算以本机配置和明确接纳记录为准；耗尽后需要本人明确追加，旧任务余额不会自动转给新任务。

### 验收、返工与试玩

交付时核对实际变更文件、测试数量与退出码、源码版本、PR 状态、遗留项和预算用量。是否合并 PR 由你决定。发现缺陷时，引用原任务消息并真实 @ 总管，说明操作、实际结果和预期结果：

```text
@示例总管
请返工这项任务：输入关键词后点击搜索，列表没有变化。
预期只显示名称包含该关键词的商品。请修复并补充回归测试，再回传结果，暂不合并。
```

Hermes 负责把返工要求送入原 DSH 会话，并监督修复、测试和结果回传。任务已结束时，Hermes 先说明后续工作及预算安排。

当前试玩服务需要 DSH 在获准任务内启动，或由你按项目 README 手动启动。总管尚无独立的预览启停入口。手动启动的服务应由启动者正常关闭；页面可打开不代表其他设备也能访问。

## 当前开发流程

用户在飞书真实 @ 总管，提出需求、回答问题或反馈试玩缺陷。Hermes 确认目标仓库，派发仓库级工作，组织给 DSH 的提示词，监督执行并引用原消息回传结果。

每项完整工作对应一个总 Issue、一张原生 Kanban 卡和一个 DSH 会话。会话登记到已绑定本地目录的 DSH 工作区，用户可以在现有 Desktop 中查看提示词、工具调用、测试结果和状态。DSH 负责细拆 Issue、开发、测试、提交及创建 PR。

负责人层级与开发能力分别配置。没有仓库的总管只派发和汇总；仓库负责人只处理明确分配的本地项目。同一工作内的答复、返工和继续保持原会话、历史、工作区与账本。

业务验收只从飞书正常入口推进。监督者可以只读核对状态；后台 RPC、CLI 或内部工具推动的业务操作属于调试，不能冒充用户流程通过。

## 飞书问答与审批

普通问答与规划确认关联原问题轮次，支持分次回答。用户引用消息并真实 @ 发问机器人；目标不能唯一确定时先澄清。重复、失效、错投和未知发送结果不盲重送。

DSH 具体执行审批使用飞书卡片，只提供“批准一次”和“拒绝”。插件核对本人、原通知、工作、会话、连接代次及原操作，分别显示决定和实际工具结果。文本答复保留为备用入口。

Hermes 原生命令确认使用独立的原生协议。`/new` 等命令提供“一次批准”“始终批准”和“取消”。“始终批准”会改变后续确认设置，卡片明确展示持久影响；处理后停用按钮。重置 Hermes 对话不替换 DSH 任务会话或账本。

## 监督与交付

有活动工作时，每 5 分钟或新增 10 次 DSH 请求检查一次，先到者触发。Hermes 核对当前进展、阻塞和用量，决定是否立即引用原消息回传。需要本人处理的问题、审批和交付及时通知，无活动不刷屏。

检查点不结束执行。插件不额外设置固定的 30 分钟截止、单次输出或累计 token 配额。本人明确配置的请求数或其他预算仍按原账本执行，取消某项限制不重置已用额度。

总 Issue 验收核对实际文件、测试命令及退出结果、固定源码版本、细票、PR 和遗留项。模型自报完成、受理成功、观察器就绪或卡片状态不能单独证明交付。PR 审查和合并状态单列，远端更新后核对相应本地分支。

停止只处理插件负责的会话和原生作业，保留代码和历史。执行范围或清理结果未知时保留仓库占用，不关闭共享 DSH 或其他会话。重载和 worker 重排先核对原工作，未知输入不重复发送。

## 安装与资料边界

包只使用 Hermes 主插件入口及主包中的 DSH Hook。Hermes 和 DSH SDK 源码保持原字节。当前配置必须明确启用 `simple_development`，并注入已核验的本人身份、飞书绑定、原生 Kanban、本地仓库及共享 Desktop 引用；未配置时不启用旧管理系统。

安装及版本更新使用 Hermes 原生安装器。记录准确版本、差异、备份、回退和实际加载证据；相同授权范围内的候选更新不因 SHA 变化重复申请批准。磁盘安装成功与原会话实际加载分别核验。

真实绑定和凭据保存在仓库外受限本机配置中。原生日志可以保存非秘密运行信息，凭据不进入普通日志、群消息或公开产物。源码、示例和公开记录使用合成引用。

当前范围不包含独立 `DSH_HOME`、第二套派发队列、自建 Dashboard、完整聊天镜像、Desktop 手动接管或资料迁移。旧实现和旧失败作为历史保留，不作为当前启用功能或通过证据。

## 发布状态与验证

当前已取得同一个 Desktop 会话中的真实单仓开发、返工、实际测试、PR、浏览器试玩、正常清理和原群引用回传证据。新版分项查询和进度通知引用也已实测。

本轮确认范围的开发与真实验收已收口。多仓协调、分次问答、停止后交接及待答恢复以对应验收记录为准。旧方案和旧失败继续保留；当前试玩服务的启动限制见上方使用指引。

本机验证沿用已通过的有效结果。新增修改先定点，再验证受影响范围；相同源码、环境和命令只保留一个有效长测。远端 CI 是静态补充检查，不作为本机个人使用的发布硬门禁。
